How it works

Mandarin is a server and an Android app. The server scans your library and plays it to Sonos rooms, UPnP/DLNA streamers, Mandarin Bridges and the Android app.

Tracks go into the speaker's own Sonos queue; a streamer is handed each next track ahead of time. Each device fetches the audio from the server: the file itself when it can play it, converted to what it takes when it can't.

  • Library. The music folders are walked and every audio file's tags are read into a database (SQLite). Albums are decided a folder at a time, so a folder of tracks by different artists with no album-artist tag becomes one compilation, and CD1/CD2 folders become one album. Covers come from cover.jpg/folder.jpg/… or the first track's embedded picture, resized once per size and cached; an album with no cover gets one drawn, with its title. The pictures are drawn with ffmpeg. Rescans only re-read files whose size or date changed, on the cores playback doesn't keep.
  • Album names. The identification scan looks each album up by what its files carry (a release id, barcode, catalogue number, ISRCs), then by name on MusicBrainz and iTunes. It scores each release against the tracks and their lengths, and lays the names over the album, never on the files, with the MusicBrainz pack, loudness measuring and the waveforms alongside. Every MusicBrainz request waits its turn on one timer, and while MusicBrainz is turning requests away every lookup pauses (a minute, then twice as long each time, an hour at most).
  • Credits and artists. In the background, one album and one act at a time at MusicBrainz's pace, the server reads who played, sang, wrote and made each album from its tags and its MusicBrainz release, and who each act is (members, years, place, links) from MusicBrainz and Wikidata, with a picture from FanArt.tv, Wikidata or Deezer. A page asked for before it gets there is looked up there and then, as the act its albums are by: the MusicBrainz id in their tags or matches, else the act MusicBrainz lists for their titles. Names found to share a MusicBrainz id are one artist, written as MusicBrainz names them; two acts of one name with their own ids are two. Kept in the database; your files are not changed.
  • Streamers. Found on the network by SSDP, each one's description read for what it can play (plus a WiiM's own API), every device kept in a register with your names and settings, and played through its own transport (AVTransport): the queue kept on the server, the next track handed over ahead of time (gapless where it supports it), changes arriving by UPnP events. The stream plans decide what each device gets: the file itself within its ceiling, FLAC at its highest rate or upsampled in 64-bit float otherwise.
  • Sonos. One speaker is found over SSDP and the whole household is read from it (ZoneGroupTopology). A Sonos group is a zone (its coordinator owns the queue) and each room is an output (volume and mute are per room). Tracks go into the coordinator's own Sonos queue, with the DIDL-Lite metadata Sonos insists on, so the speaker moves between tracks by itself. The queue you see is read back from the speaker, so anything added from the Sonos app appears too. Ported from Caldera Sonos Bridge and the UPnP to Sonos bridge, by the same author.
  • Audio. Each queued item is an address on the server. Within 24/48 it serves the file as stored, with byte ranges; above that, ffmpeg writes FLAC 24/48 to the cache and the speaker is served from the growing file.
  • The interface. Mandarin's own page, served by the server and shown in the browser and the iPhone home-screen app, talking to the server's /api. The Android app draws the same screens natively and asks the same /api.
  • The server. One program in C# (.NET, built to a single self-contained file: no .NET or Node.js needed to run it). It began in v0.8.1 as a front door before the original Node.js server, took its parts over one by one with each held to the Node server's own answers, and has been the whole server since v0.9.0.

For how your music is found and named, in plain words, there is a guide on Downloads.

Sound devices on the server

On Linux, Mandarin plays no sound device of its own (v1.2.1). A USB DAC on the computer Mandarin runs on is played by Mandarin Bridge for Linux, installed beside it with one line, and the DAC is a room of its own in Settings → Audio Devices. On Mandarin OS, choose Mandarin Bridge as it installs, or Install it from the system page's Settings tab. The server used to open the computer's sound cards itself (ALSA), kept losing the DAC and competed with the Bridge for it. A card it had in Audio Devices is forgotten by itself.

Playback comes first

On Linux with three cores or more, playback (what Mandarin makes as a track plays: its conversion, upsampling or DSD) keeps a core of its own, or two while DSP is in use (the last ones), and the server runs on the others. Scanning, measuring ReplayGain, the tag reader check and the phone's downloads run at the lowest priority, their disk reads last; conversions made ahead of play run just below playback. Settings → Library Scanner → Processor shows the split. PLAYBACK_CORES=1 or 2 fixes how many cores playback keeps, 0 shares every core; PLAYBACK_CORE=<n> picks the core.

Building and testing

The source is on GitHub: the server in server/, the page in public/, the Android app in android/, Mandarin Bridge in bridge/ and Mandarin OS in os/.

./server/build.sh   # the server (.NET 10 SDK) into server/bin/mandarin-server
./engine/build.sh   # the audio engine (.NET 10 SDK and clang), for Mandarin Bridge for Linux
MUSIC_DIR=~/Music PORT=3500 server/bin/mandarin-server

npm ci              # the tests' own packages (Node.js 22: the tests are JavaScript, node:test)
npm test            # unit tests + end-to-end runs against a fake Sonos household and fake UPnP renderers
npm run gates       # the quality gates (docs/quality-plan.md)
  • The end-to-end test starts two fake Sonos rooms on 127.0.0.11/12:1400, plays a CD-quality album and a 24/96 album through the real server, and checks what the "speaker" fetched: bit-perfect FLAC for the first, FLAC 24/48 for the second. It needs ffmpeg on the PATH (or FFMPEG_PATH).
  • The browser tests open the page itself in headless Chromium or Chrome — at a desktop with a mouse, a phone and a tablet — and check Home, the album view and Now playing. They use the browser already installed (or CHROME_PATH), with no extra packages, and are skipped where there is none.
  • Every route the server answers is listed in docs/specs/api.md: its method, its address, who may ask and the file and line that answers it. node tools/api-map.js write writes it from the sources, and the gates fail while it is out of date.
  • The site's languages: npm run i18n writes every marked text of these pages into docs/i18n/en.json, the translators' source; the tests fail while a language file's keys or its links, code and markup differ from it.
  • Building the Mandarin OS image yourself: os/README.md.
