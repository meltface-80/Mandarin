  `workflow_dispatch`; any tag trigger is filtered to `'v*.*.*'` (release.yml also checks that

  migration, tell them what to do (section 6).

  three steps from here (section 3).
- **No new work in Node** except the plumbing that hands a job over. **Pages stay HTML/JS; tests
  stay JS** (`node:test`).
- **Never put an AI model's name or identifier** in commits, PR titles or bodies, code, comments
  or docs. Use the commit and PR attribution lines your own session gives you; end every GitHub
  comment with `\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_`.
- **Android:** "provide a new android app where needed". A push to migration that changes
  `public/` or `android/` (a version bump does) puts its APK on the rolling **test-android**
  pre-release (android.yml). No tag is made.
- Write for the owner in plain words; the CHANGELOG opens each version with what they'll notice.
- **The quality gates** (`docs/quality-plan.md`, CLAUDE.md section 5, since stage 5): `npm run
  check` green before every push; the ratchet's files and the baselines only shrink; every new
  server module opens with `// @ts-check`. The owner asked for the same gates in both their
  repositories; Rouen's are in its `dev` branch (its PR #202, `dev/quality.md`), and these match
  them in shape and in command names.

## 4. How the server is laid out (since v0.9.0)

- One program, `server/Mandarin.Server` (.NET 10, ASP.NET Core slim, SQLite), set up from the
  environment (`Config.cs`), its background work in `Jobs.cs`, its library state in
  `Library.State.cs`. `server/README.md` says how it runs and records how each part moved.
- No Node server: the history of the hand-over (the jobs named in three places, `/internal/front/runs`,
  `ctx.madeByFront`, `MANDARIN_FRONT`) is in the spec and the CHANGELOG only.
- The tests are JavaScript (`node:test`) and start the program (`test/server.js`), or ask its rules
  directly (`mandarin-server score`, `test/score.js`). The parity suites hold it to the Node
  server's answers as they were kept (`test/golden.js`, read-only, `test/golden/*.json`); there is
  no way to record them again.
- The `/internal/` addresses left are the tests' (front key, loopback): `/internal/jobs/*`,
  `/internal/library/changed`, `/internal/playback/revision`, `/internal/mb/slot`.
- **Traps:** `MANDARIN_CPU_HOLD_MS` shortens DSP's ten-minute hold for tests. The fixture library
  has **7 files** in 3 albums; moving a folder *within* the music root reads as "moved", not gone —
  move it out (`lib.root`) to get `offline_dirs`.

## 5. How to finish a stage

1. Bump the version: package.json (and `npm install --package-lock-only`), README.md's title, the
   site's badge (`docs/index.html`), `android/app/build.gradle.kts` (versionName, and versionCode =
   300 + the patch number from 0.9.0, e.g. 0.9.1 → 301; it was 200 + the patch for 0.8.x).
   `test/version.test.js` checks they agree. Add a CHANGELOG entry at the top, in the same style.
2. Rebuild **both** `./engine/build.sh` and `./server/build.sh` after the bump; the engine test
   checks the engine's version.
3. `npm run gates` (the file-length ratchet, `@ts-check` and `tsc`, ESLint against its
   suppressions; `npm run tools` once per clone first). A file that grew past its allowance is
   split, never re-accepted; a new module carries `// @ts-check`. Then the whole suite, to a file:
   `npm test` (four files at once). Run it in the background and do docs meanwhile; on this box it
   takes about half an hour.
4. Push, open a PR into `migration` with a plain summary and test results, then watch CI. CI
   jobs: **Quality gates**, **test (22, part 1/3 to 3/3)**, **Tests on a Mac (part 1/2, 2/2)**,
   **Build image** (it fails if Node.js is in the image), and Android's **APK / Core tests (JVM) /
   Tailscale engine tests**. A run takes 15–25 minutes.
5. Have the change reviewed (an agent reading the diff for bugs found real ones in stage 4b), fix
   what's real, then squash-merge into `migration`.
6. Tell the owner what to do in Dockge (section 6) and what to try.

## 6. What the owner does in Dockge

Their stack's compose file uses `image: ghcr.io/meltface-80/musicd-server:migration` (the repo's
`docker-compose.yml` shows `:latest`; the rest of it is theirs and stays as it is, especially the
`musicd-server-data` volume).

- **First time on migration:** in Dockge, open the stack → **Edit** → change the image tag from
  `:latest` to `:migration` → **Save** → **Update** (pulls and recreates).
- **Each later stage:** wait until `:migration` is published (the docker-publish run after CI on
  the merge), then open the stack → **Update**. Check `http://<server>:3500/api/health` shows the
  new version.
- **A stage tried before its merge** (if the owner asks; they chose one final test after stage 7
  instead): the image for a `stage-*` branch is
  published as `:<branch>` after CI passes on its last push (`.github/workflows/docker-publish.yml`),
  so set the tag to, say, `:stage-6-playback` → **Save** → **Update**; once the stage is
  squash-merged, back to `:migration` and **Update** as usual. The queues one server kept are
  put back by the other, so nothing is lost across the switch.
- **Going back:** set the tag to `:latest` (v0.8.44) and **Update**.
- **Android:** the test app is the `.apk` on GitHub's **test-android** pre-release (Releases page).

## 7. Things that will trip you up here

- **4 cores.** `npm test` runs four files at once. The whole-file hangs seen before (a fake's `close()` waiting on a
  connection the C# server still held) are fixed (v0.8.49, `test/fixtures.js` `stopServer`), and
  a request a server never answers fails after a minute and a half naming its address
  (`test/setup.js`): if a run stops producing output, read the log for that line.
- **Agents you start share the account's usage limit** and have hit it mid-task. Make them commit
  and push after every part.
- **node_modules is a symlink** in worktrees, ignored through `.git/info/exclude`. Add files by
  name: `git add -A` fails on it.
- `pkill -f <pattern>` can match your own shell; kill by PID from `pgrep`.
- The git proxy refuses deleting remote branches and writes to the repository's settings
  (rulesets); `gh api` reads work, `gh api` job-log downloads don't. Use the GitHub MCP tools; a
  job's log comes back as its last 5,000 lines at most, which is why every test job prints the
  failed tests again at the end (`.github/failed-tests.sh`): read the tail for them.
- A test that hangs no longer holds a CI job to its 25-minute limit: the runner gives each test
  five minutes and exits a file whose process lingers (`--test-timeout`, `--test-force-exit`, in
  `npm test` and ci.yml). One such hang, in a child that never printed, happened on stage 5's
  last run and passed on a re-run; if it comes back it will now fail by name.
- `test/lastfm.test.js` measures Last.fm's spacing at the far end (≥ 240 ms). C# spaces asks from
  the *answer* now (v0.8.47).
- **test (20), when there was one, twice failed `test/backup.test.js` with EADDRINUSE** on its own port, at the
  server started after a restore's restart, while the next test's server took the same port a
  moment later. Not reproduced here (twelve runs under load; a thousand close-and-listen-again
  rounds in one process), and the same commit passed in its other CI run. The test's `server()`
  now puts `lsof`'s view of the port in the error, so the next failure names the holder: read it
  before anything else.
- Never skip, disable or loosen a test to get green; find the cause.
